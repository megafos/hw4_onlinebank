# Домашнее задание 4 - платформа уведомлений онлайн-банка

Комплект содержит архитектурное решение централизованной платформы уведомлений: требования, RFC доставки критичных сообщений с переключением push → SMS → email, два архитектурных варианта, расчёты и проверяемую модель части алгоритма.

Главные документы:
*  `notification_platform_requirements.docx`
* `notification_platform_rfc.docx`

Для каждого документа в папке `supplementary` находится версии в md и pdf форматах.

Избражения для всех созданных диаграмм сделаны на основе Mermaid и PlantUML кода. Данный код приведен в папке `diagrams`. 
Для создания и рендеринга диаграмм итспользовался VS Code c extensions.

## Архитектура и границы решения

Вариант 1 использует Kafka и автомат состояний в PostgreSQL. Вариант 2 использует долговечные workflow Temporal. Предлагается вариант 1 при наличии компетенций Kafka/PostgreSQL.

**ВСЕ ОПИСАННОЕ НИЖЕ ЯВЛЯЕТСЯ ОПЦИОНАЛЬНЫМ.**

И в целом папка `supplementary` и ее содержимое являются опциональными. Для данного домашнего задания она не требуется, но представлена в качестве дополнительных полезных материалов.

## Контракты platform_interfaces

### api.yaml

Спецификация OpenAPI 3.1: HTTP-операции, запросы, ответы, коды ошибок и аутентификация.

| Метод и путь | Назначение |
|---|---|
| `POST /v1/notifications` | Устойчиво принять уведомление |
| `GET /v1/notifications/{notification_id}` | Получить статус с проверкой прав |
| `POST /v1/notifications/{notification_id}/ack` | Принять ACK push от приложения |
| `POST /internal/v1/provider-receipts` | Принять нормализованный результат от доверенного адаптера |

При приёме 202 означает новое сохранённое обязательство, 200 - корректный повтор с прежним ID, 409 — конфликт содержимого, 503 — невозможность устойчивого приёма. Это контракт для согласования и документации, а не реализация сервера.

### notification.schema.json

JSON Schema тела запроса создания уведомления. Обязательные поля: `event_id`, `recipient_id`, `purpose`, `type`, `template_id`, `template_version`, `payload_ref`, `occurred_at`, `expires_at`. Заданы типы, длины, категории, формат времени и запрет лишних полей. `producer_id` берётся из аутентификации.

Схема не проверяет существование получателя, полномочия, доступность шаблона или взаимный порядок временных отметок: это ответственность приложения. OpenAPI ссылается на этот файл, поэтому их нужно хранить рядом.

### notification.sample.json

Учебный пример уведомления о завершённом переводе с актуальностью 24 часа. Демонстрирует формат и используется при проверке JSON Schema. Он ничего не отправляет. Фиксированные даты подходят для проверки структуры.

### db.schema.sql

Исходная PostgreSQL DDL-схема.
Содержит таблицы:

| Таблица | Назначение |
|---|---|
| `notification` | Логическое уведомление, бизнес-ключ, состояние, версия и сроки |
| `delivery_attempt` | Попытки по каналам и ключи запросов провайдерам |
| `receipt` | Подтверждения и результаты доставки |
| `outbox_event` | События для последующей устойчивой публикации |
| `inbox_event` | Учёт обработанных событий для дедупликации |
| `scheduled_wakeup` | Сохранённые таймеры |
| `audit_event` | История переходов и их причины |

## Расчёты и проверки platform_validation

### capacity_planning.py

Рассчитывает нагрузку платформы, а не измеряет фактическую мощность серверов. Рассматривает 3 млн DAU и чувствительность при применении тех же интенсивностей ко всем 10 млн MAU. Вычисляет количество уведомлений, попыток, записей, объём Kafka/истории/аудита, условную стоимость SMS/email. Дополнительно сохраняет проектные пики, скорость кампании, backlog.

Выводит расчёты в терминал и создаёт `capacity_planning_output.py` рядом с собой. Этот выходной файл содержит корректную Python-переменную `RESULTS` со словарём результатов; это данные, не тест и не скрытый JSON с другим расширением. Его не требуется запускать.

### capacity_planning_validation.py

Проверяет функцию `calculate()` из `capacity_planning.py`. Один тест содержит шесть проверок:

| Показатель | Ожидаемое значение |
|---|---:|
| Входящий поток при 3 млн пользователей × 10 событий | 30 млн/сутки |
| Альтернативный поток при 10 млн пользователей | 100 млн/сутки |
| Базовые логические записи критичного потока | 38,88 млн/сутки |
| Сырая история критичного потока за 30 дней | 280,8 GB |
| Условная стоимость внешних отправок | 1 201 200 денежных единиц/сутки |
| Отношение хранения для двух сценариев | 10/3 |

Сохраняет протокол в `capacity_planning_output.txt`.

### notification_delivery_model.py

Исполняемая модель части правил доставки критичного уведомления. Класс `Delivery` использует локальный SQLite, класс `Conflict` сигнализирует о повторном ключе с противоречивыми данными. Таблицы модели `notifications`, `attempts`, `receipts` создаются самим кодом, а не из PostgreSQL DDL.

| Метод | Назначение |
|---|---|
| `__init__`, `connect`, `transaction` | Подключение, создание таблиц и атомарность изменений |
| `accept` | Приём с дедупликацией по отправителю, событию, получателю и назначению |
| `state`, `attempts` | Чтение состояния и истории попыток |
| `advance` | Переход по актуальному таймеру, следующий канал, истечение срока или WAITING_RETRY |
| `claim` | Последняя внутренняя проверка перед началом отправки |
| `transport_result` | Запись ACCEPTED, UNKNOWN либо FAILED |
| `receipt` | Применение подтверждения или ошибки с дедупликацией |

Маршрут по умолчанию push → SMS → email. 

Время передаётся числом секунд. 
Нет настоящих HTTP-вызовов, Kafka, Temporal, планировщика и проверки криптографических подписей.

### notification_delivery_validation.py

Пятнадцать тестов модели: повторный и конкурентный приём, конфликт содержимого, повторный таймер, конкурентный failover, UNKNOWN без слепого повтора, поздний ACK до/после начала SMS, дедупликация receipts, монотонность успеха, истечение срока и поздний успех, сохранение состояния при повторном открытии файла, запрет недоверенного подтверждения, запрет начала после срока и отсутствие ложного успеха при исчерпании маршрута.

### platform_interface_validation.py

Проверяет корректность JSON Schema, OpenAPI 3.1 и синтаксис SQL.
Сохраняет вывод в `platform_interface_validation_output.txt`.

### Файлы результатов

| Файл | Что подтверждает |
|---|---|
| `capacity_planning_output.py` | Воспроизводимый набор расчётных оценок в `RESULTS` |
| `capacity_planning_output.txt` | Фактический результат одного теста арифметики |
| `notification_delivery_validation_output.txt` | Фактические результаты 15 тестов модели |
| `platform_interface_validation_output.txt` | Результат проверки четырёх файлов интерфейсов |


## Как запускать

Команды выполняются из корня `hw4_onlinebank`. Нужен Python 3.10 или новее. 

Linux/macOS:

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install PyYAML==6.0.3 jsonschema==4.26.0 openapi-spec-validator==0.9.0 pglast==8.8
```

Windows PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install PyYAML==6.0.3 jsonschema==4.26.0 openapi-spec-validator==0.9.0 pglast==8.8
```

После активации можно везде использовать `python`. Команды ниже показывают вариант `python3` для Linux/macOS.

**Проверка интерфейсов:**

```bash
python3 supplementary/platform_validation/platform_interface_validation.py
```

Создаёт или перезаписывает `supplementary/platform_validation/platform_interface_validation_output.txt`, одновременно показывает протокол в терминале. При ошибке проверки сохраняет traceback и завершает работу с ненулевым кодом.

**Проверка расчётов:**

```bash
python3 supplementary/platform_validation/capacity_planning_validation.py
```

Создаёт или перезаписывает `supplementary/platform_validation/capacity_planning_output.txt`. Для пересчёта самих данных отдельно нужно выполнить:

```bash
python3 supplementary/platform_validation/capacity_planning.py
```

Эта команда создаёт или перезаписывает `supplementary/platform_validation/capacity_planning_output.py`.

**Проверка модели доставки:**

```bash
python3 supplementary/platform_validation/notification_delivery_validation.py
```

Создаёт или перезаписывает `supplementary/platform_validation/notification_delivery_validation_output.txt`. Оба тестовых скрипта выводят протокол также в терминал и возвращают код 0 при успехе, ненулевой - при ошибке теста. Результаты всегда записываются рядом со скриптами, независимо от текущей рабочей папки, каталог должен быть доступен для записи.
